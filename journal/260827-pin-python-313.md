# CI was testing on a Python production doesn't run

**Date:** 2026-08-27
**Branch:** `chore/pin-python-3.13`

## What was wrong

`pyproject.toml` declared `requires-python = ">=3.13"` and the repo had no
`.python-version`. `uv` therefore resolved the newest interpreter satisfying
that range. On a GitHub runner, where no matching interpreter is preinstalled,
that meant downloading and using **Python 3.14.7**.

Production runs **3.13**: `Dockerfile:48` pins
`python:3.13-slim-bookworm` by digest, and the builder stage uses
`ghcr.io/astral-sh/uv:python3.13-bookworm-slim`.

So the test suite that gates the deploy — via `ci-gate`, which the `main`
ruleset requires — was running on a different Python major than the image it
was gating. A 3.14-only regression would have passed CI and shipped; a
3.13-only regression would have been invisible to CI entirely.

Local development was on 3.13, so the drift was three-way: dev 3.13,
CI 3.14, prod 3.13.

## How it surfaced

Indirectly, and that is the point — nothing was watching for it. While
debugging an unrelated CI-only test failure on PR #99, comparing the local and
CI pytest headers showed `Python 3.13.11` against `Python 3.14.7`. The Python
difference turned out **not** to be the cause of that failure (it was rich's
colour detection, see `260827-help-test-ansi-ci-divergence.md`), but the
mismatch it exposed was real and worth fixing on its own.

## The fix

Added `.python-version` containing `3.13`, and a comment on `requires-python`
recording the distinction: `requires-python` is the *support floor*,
`.python-version` is the interpreter dev, CI and the image actually use.

`requires-python` was deliberately **not** tightened to `<3.14`. That would
assert the project does not support 3.14, which is a claim nobody has tested,
and it would force a lockfile re-resolution for no benefit. Pinning the
interpreter is the narrower and more honest change.

## Verification, and its limit

Locally, `rm -rf .venv && uv sync --locked` selects 3.13.11 with the pin in
place. The counterfactual does **not** reproduce here: removing
`.python-version` still yields 3.13.11, because a 3.13 is already installed on
this machine and `uv` reuses it rather than downloading a newer one. The
condition that produced 3.14 on CI — no matching interpreter present, so `uv`
fetches the newest satisfying `>=3.13` — cannot be recreated locally without
uninstalling 3.13.

CI is therefore the real verification: the `backend` job's pytest header names
the interpreter, and it must read 3.13 rather than 3.14. Checked on this
branch's run before merging.

## Worth remembering

An open-ended `requires-python` is not a pin, and `uv`'s choice depends on what
is already installed — so the same command gives different interpreters on a
developer's laptop and a fresh runner. If prod pins a Python version in its
image, the repo should pin the same one for dev and CI, or the gating suite is
testing something other than what ships.
